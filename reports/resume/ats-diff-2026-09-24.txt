3. BLOCKER — .docx master cannot be synced via "edit runs in place"
=====================================================================
Task instruction (step b) was: "Sync the .docx master with python-docx so
its text equals approved.txt: edit runs in place preserving formatting
(don't rebuild the document)." This is not achievable as scoped. Evidence:

  .assets/resume-sources/Gaurav_Gandhi_Resume_2026.docx has 47 non-empty
  paragraphs. Diffing its paragraph text against approved.txt's 49 lines
  (whitespace/punctuation-normalized, difflib.SequenceMatcher) finds only
  6 of 47 docx paragraphs correspond to anything in approved.txt at all —
  and all 6 are bare section headers (GAURAV GANDHI, PROFESSIONAL SUMMARY,
  PROFESSIONAL EXPERIENCE, RESEARCH, EDUCATION, CERTIFICATIONS).
  SequenceMatcher ratio: 0.125.

  Concretely, the docx is a materially different, older resume revision,
  not a near-match needing wording tweaks:
    - Title: "Senior Data Scientist" (docx) vs "Lead Data Scientist"
      (approved) — a role that doesn't exist in the docx at all.
    - Uber/Indium experience: 2 roles in the docx (Senior Data Scientist
      May2025-Present, Data Scientist Jun2024-May2025) vs 3 roles in
      approved (Lead Data Scientist Aug2026-Present [new], Senior Data
      Scientist May2025-Aug2026, Data Scientist Jun2024-May2025) — an
      entire role-block, with its own bullets, is structurally absent.
    - Every experience/research/project/skills bullet has substantively
      different wording between docx and approved, not just numbers.
    - Section names differ: "SELECTED INDEPENDENT PROJECTS" (docx, 9
      projects, long-form) vs "APPLIED AI PROJECTS" (approved, 5 projects,
      Live/Code-link format); "KEY TECHNICAL SKILLS" (docx, 6 categories)
      vs "TECHNICAL SKILLS" (approved, 6 categories, different wording and
      split); Education is 4 docx paragraphs (degree + GPA/location on
      separate lines) vs 2 approved lines (degree+GPA inline, dates
      right-aligned); Certifications is 1 docx paragraph vs 3 approved
      bullet lines.

  "Edit runs in place" assumes a 1:1 paragraph correspondence that simply
  doesn't exist for the ~90% of the document that isn't a section header.
  Doing this for real would mean inserting/deleting paragraphs, copying
  styles, and rebuilding the Experience/Projects/Skills/Education sections
  from scratch — which is exactly the "rebuild the document" the task
  instruction explicitly excluded, and a materially larger, more
  judgment-laden change (paragraph styles, run formatting, bullet list
  definitions) than "edit runs in place" was scoped to authorize.

  This is not a new problem: PR #225's own commit (48233ac) already found
  and recorded this same fact ("docx ... turned out to predate the current
  public/resume.pdf by five weeks ... missing PROJECTS/SKILLS content that
  IS in the shipped PDF") and deliberately chose direct PDF text surgery
  over editing the docx for exactly this reason ("doing so and
  re-exporting would have regressed the resume, not precision-edited it").
  This session's diagnostics quantify that same finding (6/47 paragraphs,
  ratio 0.125) rather than override it.

  Full paragraph-level evidence: see the scratch file (not committed, not
  needed as a permanent artifact) built via python-docx + difflib in this
  session; the same figures (6/47, ratio 0.125) and the full list of
  unmatched docx paragraphs are reproducible by re-running the diagnostic
  against .assets/resume-sources/Gaurav_Gandhi_Resume_2026.docx and
  reports/resume/approved-2026-09-24.txt.

4. Why content/resume-data.json / content/resume-metrics.json were NOT
   edited in this session (deviation from the literal step-a instruction)
=====================================================================
scripts/check-resume-pdf-consistency.mjs (wired into CI) reads
public/resume.pdf's actual text and fails if a resume-data.json project
entry's numeric tokens aren't found anywhere in the PDF. Updating
resume-data.json's Samidha-Reviews/ReviewIQ entry to 78.6% now, while
public/resume.pdf still says 83.8% (since the PDF itself is blocked, see
above), would make that check fail on this branch — "78.6" wouldn't be
found in the PDF text. Held this edit until the PDF can actually be
regenerated in the same change, per this repo's own rule (CLAUDE.md /
the wider rule that a scorer/metric-surface change and its published copy
regenerate together, never as a separate follow-up step) — the two must
land together or not at all.
